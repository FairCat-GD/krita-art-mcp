## 2. What holds

## 3. Findings

### High

**F1. The banned-call scan blocks session 7's raster selections as planned.**
Block 7 sends raster masks to the plugin raw and builds the selection on a fresh `Selection()`
(`SESSIONS.md:1501-1508`); PDD K11 names the call, `Selection.setPixelData` reads w×h bytes
(`PDD.md:497`); `bridge_core/transfer.py:74-105` already implements `take_mask` for it. But the
scan refuses any attribute named `setPixelData` (`tests/plugin/test_source_scans.py:15, 71, 149`),
because invariant 1, "no raw pixels into a *layer*" (`SPEC.md:220-223`), cannot be told apart
from a selection write by name. The PDD's decision log names what the invariant rejected:
"`Node.setPixelData` / arbitrary Python" (`PDD.md:703`), not selections. Session 7 would have had
to break the scan or the design. *Remedy:* allow `setPixelData` in one adapter function only, on
a receiver that function built with `Selection()`, with an AST test holding both rules; banned
everywhere else. The invariant keeps its wording.

### Medium

**F2. The bridge keeps every finished operation for the Krita session, reads included.**
`bridge_core/jobs.py:92-96` (`_operations`, `_requests`, `_bound`) and `:188-194` (results kept,
args dropped). The server mints a `req-<uuid>` for every read (`bridge_client.py:123`), so each
`server_info`, `capture` and `sample` adds entries nothing removes until Krita quits, and
`_bound` outlives released ids (`:95-96`). A painting day is thousands of strokes and captures
inside a Krita the owner keeps open for days. Review 2 skipped it as "Session 3's call"; session
3 kept everything. *Remedy:* bound retention for operations whose id the server minted (reads
need no dedup; keep until first delivery plus a window), and measure Krita's memory after N-01's
run.

**F3. The journal's read path decodes seven days of full stroke arguments.**
`journal.py:166-187` reads every whole day file on the first lookup and `json.loads` each line;
`dispatched` stores `args` in full (`:88-114`, as PDD Part 6 wants: "point arrays stored in
full"); every request's receipt stays in memory (`:229-230`); only `args_sha256` is indexed
(`:212`). A 4096-point stroke is ~100–200 KB per line; a busy week is hundreds of MB decoded
inside the first journaled call of every server process, under the call lock and the 45 s
budget. No measurement exists. *Remedy:* measure journal size and first-lookup time after the
N-01 run; if it bites, keep the index lines small and the arguments in a sidecar per operation.

**F4. The adapter's branching logic has no tests, and the probe reaches part of it.**
`krita_adapter/documents.py` (571 lines) has no unit tests by design (SPEC §6: libkis is out of
reach), but some of it is pure logic. `_unmasked` (`:284-293`) picks the node to activate for
K46; its global-selection-mask branch (`:290-292`) is reached by no probe check (the live K46
check uses a local mask on `probe base`). `bring_forward`'s failure paths (`:176-179`), `create`'s
cleanup (`:44-46`) and the batch-mode restores (`:52-57`, `:211-216`) are untested anywhere.
*Remedy:* move the node choice into `bridge_core` as a pure function over `tree()`'s dict (one
home, testable), leaving the adapter `setActiveNode(_node(id))`; optionally a stub `krita`/PyQt
module under `tests/plugin/` so the adapter imports under pytest.

**F5. The server instructions stand at 2,773 of 4,096 characters after five sessions.**
`instructions.py`, measured. PDD Part 4 (`PDD.md:328`) leaves at least eight rules for sessions
7, 8, 9, 11 and 14: add a layer before painting; the inherit-alpha recolour; the union mask then
each selection; one stroke per call; `input_fallback` and flat strokes; previews after one to
three strokes; which undo steps exist; the owner must not edit presets. At the current density
that is 1,200–1,500 characters, and decision 30 says session 14 finalises under the cap.
*Remedy:* a character budget per remaining tool session (~300) and a trim of the present text in
7, so 14 finalises rather than cuts.

**F24. A POST the bridge never registered is reported `running` for ever.**
`bridge_client.py:200-205`: a POST that times out or breaks (`TimeoutError`, `OSError`) is
treated as delivered and polling begins (`:227`, `call = None`); `:211-213` tolerates a 404 for
the whole budget while nothing has yet answered `running`; `:229-230` then records the id in
`_sent` and returns `Pending`. Every later `operation()` finds the id in `_sent` (`:142-145`,
`strict=False`, a fresh `answered=False`) and loops on 404 to its own deadline, for ever, each
`krita_operation_get` holding the call lock (`tools/__init__.py:87-88`) for 45 s. A POST stuck
behind a long Krita call does register later, which is what the grace is for
(`test_document_tools.py:555-564`); one whose connection was reset or cut never does. During
session 12's 20 s saves every POST times out, so the path is routine; the trigger is the rare
reset. A retry of the *tool call* recovers, because the bridge never saw the request id; only the
operation id is stuck. *Remedy:* bound the 404 grace to a short window after the bridge first
answers in the same follow (a 404 is then "unknown"), and let `operation()` on an id never
confirmed registered say so instead of waiting out another budget.

**F25. `dirty` is set only when the handler returns; a mutation that then raises leaves the
document clean.** `registry.py:133-136`. For the coming stroke, layer and selection ops, an
unexpected libkis exception between the mutation and its verify or rollback becomes
`INTERNAL_ERROR` (`jobs.py:178-186`) with neither `dirty` nor `unsafe` set; `document.close` with
`refuse` (`documents.py:52`) then closes a working copy with an unverified change, and
`document.list` calls it clean, against PDD Part 4's definition ("a bridge mutation since the
last verified save", `PDD.md:184`). Today's rule, "dirty on success only"
(`test_documents.py:192-199`), is right for a refusal before the mutation and wrong after it.
*Remedy:* a handler marks the handle dirty before its first libkis mutation, so an exception
afterwards leaves it dirty; the verification core makes this the contract of every mutating op.

### Low

**F6. The probe's undo op switches views the way the adapter rejected.** `krita_adapter/ops.py:29`
uses `app.activeWindow()`, which review 3 replaced with `windows()[0]` (`documents.py:41, 165`)
because it can be None; `:46` restores the owner's view with `Window.showView`, which
`documents.py:172-173` says "would give its widget a new one", so the adapter uses
`View.setVisible`. `probe.undo_action` runs in every probe when no document is unsaved, and the
view it restores is the owner's. *Remedy:* share `bring_forward`/`restore_view`, or retire the
op: its measurement is recorded (session 2) and session 9 builds its own label check.

**F7. A cancelled queued job keeps its request id bound; one failed at stop releases it.**
`jobs.py:223-227` (cancel: non-retryable `CANCELLED` through `operation.fail`, no release) against
`:233-236` (stop: retryable `CANCELLED` through `_finish_failed`, "because they never ran"). Both
never ran; `:199` states the rule, "retryable means the op changed nothing". The server's default
is non-retryable (`errors.py:19`); the journal copes with both (`test_document_tools.py:209-216`).
*Remedy:* route `cancel` through `_finish_failed` with one `retryable` for `CANCELLED` on both
sides, held by a test.

**F8. Nothing holds that every op a tool sends has a receipt.** `tools/operations.py:27-41` lists
nine ops; each tool names its op in a `call("…")` literal (`documents.py:41, 64, 120`,
`pixels.py:70, 250`, `observe.py:21, 51`). A session that adds an op and forgets `RECEIPTS` makes
`krita_operation_get` answer "That operation belongs to no tool" (`:55-58`) for any such call
that came back `running`, found only if the probe hits that state. *Remedy:* one table per tool
`(tool, op, receipt, resolve)` from which the send and `RECEIPTS` both derive, or a test scanning
the literals against `RECEIPTS`.

**F9. `KritaDocuments.selection()` reads pixels without `waitForDone()`.** `documents.py:127-140`,
unlike `selection_rect` (`:152-157`) and every composite or layer read (`:124, 143, 147`).
Invariant 6 wants the wait before any read after a mutation; session 7's `selection_set` (a
`setSelection`, K8) and `history_step` make inspect-after-mutation the normal path. *Remedy:*
`waitForDone()` at the top of `selection()`.

**F10. Open's baseline read has no size bound.** `opening.py:117-119` writes the whole composite
as one BGRA8 file (`documents.py:123-125`); captures are bounded by `MAX_READ_PIXELS`
(`pixels.py:16, 32`), open is not. N-09's 8192² fixture means a 256 MB transfer file and a
256 MB `.npy` per open, written inside the job on Krita's main thread, then copied once more in
the server (`transfer.py:37`). *Remedy:* measure open time and disk with the N-09 fixture; then
decide between refusing `working_copy` opens above `capture_source_pixels`, a tiled baseline, or
a baseline written lazily for the first `preview_render` that needs it.

**F11. A handler result that is not JSON loops instead of failing.** `bridge_core/server.py:94`
serialises the reply inside the HTTP handler; a `TypeError` there is logged (`:72`) and the
client gets no reply; `bridge_client.py:204-205` treats the dropped connection as `OSError` and
polls again until the budget, then `Pending`, and `operation_get` repeats it. Handlers return
plain dicts today; sessions 8–9 add the largest results. *Remedy:* `json.dumps` the result once
in `Jobs._run` and fail the operation with `INTERNAL_ERROR` if it cannot be.

**F12. Masks never expire from `transfer/`.** `bridge_core/transfer.py:57-66` expires the plugin's
`.raw` files after an hour; a `mask-<sha>.a8` the server wrote (`src/krita_art_mcp/transfer.py:49-68`)

**F13. The probe prints no run time and checks no leftovers.** `probe/report.py:29-31` counts

## 4. Duplication and drift

Beyond §2.3: `roots.load`, `roots.inside`, `roots.resolve`, `is_live_krita` and `source_hash`
exist on both sides by design (the plugin cannot import the server) and are held to the same

## 5. The job system, the transfer path and the registry against sessions 7–12

- **Jobs.** One handler per job, re-entry guarded, cancel for queued jobs only, dedup by
  request id for the session: the stroke-verify-rollback sequence of sessions 8–9 fits inside
  one handler with no change to `jobs.py`. What changes: retention (F2), the cancel semantics
  (F7), result safety (F11), the slot's exception guard (F27).
- **Long saves.** A 20 s `exportImage` holds the GIL; every poll times out at 5 s and
  reconnects; the backlog of 64 covers three clients polling for a minute. The server's grace
  for a late registration is right for that case and wrong for a lost POST (F24).
- **Transfer.** Before, after and diff buffers for a region R are three small files per stroke;
  `verify: "full"` on an 8k master is three 256 MB files, by the agent's choice. The resolver
  pattern of session 5 (files named by operation id, found before made, `_discard` on a final
  failure) is the one for the stroke receipts' captures to reuse. Masks need an expiry (F12).
- **Registry.** `Handle` takes the undo floor, the redo allowance and the ledger as fields;
  `guarded` gives every mutation the same gate and is where protection's `LOCKED_TARGET`
  belongs. The dirty rule needs F25 before the first pixel moves. Open's baseline needs a bound
  or a measurement before N-09 (F10).
