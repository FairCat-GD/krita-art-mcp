were read cold against `FEATURE-recovery-and-construction.md` (whole) and `SESSIONS.md` (every

renderer port. The second wave read without sight of the first wave's notes, and every

journal was counted read-only, as counts alone (§7). Every claim points at `file:line` on commit
`189ba26` or at a measurement.

## 3. Findings

### High

**F1. A save whose finish never ran reports `not_applied`, retryable, while its hidden file and
pending save stay.** `finish_save` keeps whatever outcome the finish states
(`src/krita_art_mcp/tools/saving.py:104-107`: only a finish that says nothing becomes
`uncertain`). A finish refused before its marker states `not_applied` through `stated()`: a
dialog open at job start (`registry.py:183`, `krita_adapter/documents.py:31-35`), a document the
bridge no longer knows after a Krita restart, another process's lease (`registry.py:198-203`), or
`CANCELLED` at quit (`jobs.py:372-380`). That statement is true of the finish alone. The save op
has by then made the target's folder, written `.<name>.<token>.saving.kra`, dropped any earlier
pending save and set `Pending` (`bridge_core/saving.py:96-171`). The tool returns the finish's
error with the save's identity and `retryable: true` (`tools/saving.py:108-115`); `outcome_of` settles the
journal `no_effect` (`dispatch.py:77-82`); after a restart `krita_operation_get` answers
`not_applied` from that line (`operations.py:173-180`). Nothing compares the finish's session with
the save's: `finish_save` calls the bridge with no `before_send` (`saving.py:82-88`), so a finish
sent to a restarted Krita is refused `DOCUMENT_NOT_FOUND`, `not_applied`, and the hidden file
stays. Pinned as it is by `tests/test_outcomes.py:641-648`, which keeps a stated `not_applied`
without asking whether the finish's own discard verified. *Run:* a dialog opened during the save,
so the finish met it at job start: `KRITA_MODAL_DIALOG`, retryable, `not_applied`, the hidden file
beside the target, the journal `no_effect`. *Cost:* decision 5's "not_applied only on proof" is
broken at the tool level for the one tool that writes a file, and B1's block ("a crash between
ops reports `uncertain`") is false as written. *Remedy:* keep a stated `not_applied` only when
`details.rollback_verified` is true (the finish's own discard paths, `saving.py:190,197`);
otherwise report `uncertain`, not retryable, and likewise when the finish's session differs
from the save's. Same-session resends stay allowed by decision 7.

E1, L1, B1, T1 and S1 each name "Server instructions" among their docs (`SESSIONS.md:1130,1176,
1220,1258,1290`); one-line drafts measure 131–185 characters each, about 650–730 together, so E1
alone leaves under 60 and L1 cannot fit. D1's floor of 500 spare (`SESSIONS.md:571`) was not held:
C1 spent 297 and M1 158. *What can move,* measured with its bullet and newline: the inspect line
(91) into inspect's description; the capture line (108), already in capture's description; the
stroke line (178), in its description and `verify`'s; the layer_update line's tail from "if a
filter…" (205) into a `verify` description, which the field lacks, and `inherit_alpha`'s; the
fill's first clause (151), already in its description; the sample line but its last sentence
(117), already in the sample's; the "Undo steps" line (181) into `history_step`'s; open's "The
source is never written…" (74) into `mode`'s; the envelope bullet (164), typed in every output
schema. About 1,200 characters. Two phrases are pinned and stay: "45-second wait"
(`test_envelope.py:185`) and "up to 67 megapixels (8192 x 8192)" (`:188-192`). *Cost:* a
planned session is blocked as written. *Remedy:* the move, before E1, leaving at least 700 spare.

### Medium

**F3. A rollback's first undo skips the state check, so it can undo a step the op never
pushed.** `_restore` passes `known or step.after` to `move()` (`mutation.py:372`); with `known`
still None that is `step.after`, and `_shows` then compares it with itself
(`history.py:124-129`), so the first pushed step is undone on its label alone. `move()`'s own
comment says `known` is a state an earlier move in this job confirmed (`history.py:70-72`);
nothing has confirmed this one. *Run,* on `test_mutation.py`'s World: an op pushes "Add Layer",
Krita then holds a second "Add Layer" the ledger never saw, and the judge refuses. The rollback
undoes the stranger, the after-check fails against `step.before`, it redoes, and the call ends
`ROLLBACK_FAILED` with moves `['undo', 'redo']`. With `known` passed as it is: `ROLLBACK_FAILED`
with no move, the state read catching the mismatch first. Found by both reads. *Cost:* the
document is unsafe either way, but invariant 5's second clause is broken for the length of the
move, and if the redo failed the stranger would stay undone. An unknown step grows likelier with
L1's and T1's multi-step calls. *Remedy:* pass `known` as it is, or seed it from the state
`_unnamed`'s move confirmed (`mutation.py:431,436`).

**F4. A finish refused retryably can never run again under its `request_id`.** The server always
sends the finish under derived ids (`tools/saving.py:85,87,118-120`). `Jobs.submit` answers a
known `operation_id` before anything else (`jobs.py:185-188`), and a retryable failure releases
only the request (`:296-298`); the failed op stays registered under its id. *Run,* in memory
and end to end: the finish met a dialog at job start and failed `KRITA_MODAL_DIALOG`, retryable;
with the dialog closed, two retries of `krita_document_save` under the same `request_id` dedup to
the finished save and re-POST the finish under the same derived id, and both return the stale
failure; the handler ran once, one export, the hidden file still there. Every
`krita_operation_get` repeats it for the Krita session, until a new save or a close drops the
pending save. *Cost:* an agent loops on "retryable"; B1's reopen under a third derived id
inherits it. *Remedy:* in `submit`, a known op that failed retryably and whose request was
released runs afresh under its id; a test with a finish refused once.

**F5. A poll from a second server process breaks the first process's save for good.**
`krita_operation_get` runs `finish_save` for a save (`operations.py:65,89-90`). The finish runs
under the lease (`bridge_core/saving.py:229`, `registry.py:193,198-203`), so a second process's
poll is refused `DOCUMENT_IN_USE`, not retryable, before the finish's marker. That failed op now
holds the derived id (`jobs.py:185-188`) for the owning process too. *Run,* through the worlds:
server A saves with a short budget and gets `running`; server B polls that `operation_id`:
`DOCUMENT_IN_USE`, `not_applied`; A's own poll afterwards: `DOCUMENT_IN_USE`; A retrying the save
under the same `request_id`: `DOCUMENT_IN_USE`, `not_applied`; the folder holds only the hidden
file. On one shared data folder, B's `_finish_journaled` (`operations.py:192-220`) writes A's
finished line too, so A's journal settles on B's failure. *Cost:* a read-only poll from another
client kills a save, and B1's reopen would go the same way, its new document's lease to whichever
process polled. *Remedy:* finish only from the process that made the call (the owner's choice,
§6), and F1's rule for a finish refused after a completed save.

**F6. `krita_operation_get` is `readOnlyHint: true` yet can finish a save.** Its poll runs
`document.save_finish` (`operations.py:89-90`), which places the file, clears `dirty`, records
the saved state and takes the lease (`bridge_core/saving.py:208-218`, `registry.py:204`). The hint
is held as `READ` (`tests/test_tools.py:98-124`), the guide's hints table says reads "Change no
document" (`USER-GUIDE.md:82`), and `_checked` fills in no outcome for its failures
(`tools/__init__.py:106,154`). Found by both reads. By decision 1's rule the hint is untrue; it is
the one untrue hint of the 20, and the only one whose honest value is in question, since flipping
it would put Codex's review on every poll. *Landed:* the owner chose to finish only from the
calling process and keep the hint read-only, with the exception written down (§6).

**F7. The frame recovers at most one step Krita holds and the op has not pushed, and a detached
node cannot be named across two port calls.** `_unnamed` handles `labels[len(pushed)]` alone
(`mutation.py:412`), and `_pixel` needs `pushed == labels - 1` (`:398`). *Run:* labels
`(ADD, ADD)`, Krita adds two layers, the op pushes neither and raises: `_unnamed` undoes one step
against the wrong `after` state, reverses it, and the call ends `ROLLBACK_FAILED`, unsafe, the ids
not back; with one pushed and one unpushed, confirmed. `krita_adapter.documents._node` finds a
node only by walking down from the root (`:467-474`), so L1's reorder as two port calls
(`remove`, then `addChildNode` by id) gets `LAYER_NOT_FOUND`, and as one port call sits in the
two-unpushed window on any raise after the second Krita step, a `waitForDone` included. T1's
`fromXML` plus attach has the same shape. *Cost:* L1's "a failure between them must still
confirm" holds only for a raise strictly between the two steps. *Remedy:* a port method that
calls back between the steps, so the core pushes `steps.of(port.tree(document))` on the real
intermediate tree (or returns a detached handle); or `_unnamed` walking every unpushed label
newest first while each state is distinct.

**F8. The ledger's fingerprint sees only `(id, blend_mode)` and the selection**
